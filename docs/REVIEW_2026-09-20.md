## PART ONE — what landed on `main` before you left

### 1. #49 — a board now knows when its link is dead

**What it took.** `LinkHealth` as a second axis beside `ConnState`, because one enum cannot say
"the driver claims connected and it is lying". An ICMP probe ladder — gateway, then your DNS
server, then 8.8.8.8, rotating on failure so a rate-limiting router cannot convict a healthy link.
RSSI re-polled with an age stamp. `isOnline()` returns false on `LINK_DEAD`.

**How it looks different.** Before: a dead board showed full green WiFi bars for six hours. Now:
the glyph drops to a bare red stalk and the dump says `DEGRADED`.

**Your idea, and it was the right one.** The ladder was your suggestion — gateway first, then DNS,
then a known-good external IP. It is what stops one unreachable host convicting the whole link.

**What went wrong.** The probe was demand-driven, so a *healthy* board never probed, a latch never
set, and a guard would have silently disabled the entire fix on exactly the boards that needed it.
Caught by reading real serial output, not by re-reading the diff.

**Still open.** Detection works. **Recovery does not.** See Part Three.

### 2. #50 — the system drawer

**What it took.** Width from logical screen width, right-anchored, height measured from content,
four button rows, and a top offset so it hangs from whatever header is actually there.

**You corrected me here and you were right.** I proposed sizing it from the board identity macro.
You said no — use screen-relative. Board identity would have meant a new case for every board ever
added; logical width means a board that does not exist yet gets a sensible panel for free.

**It needed two follow-up fixes after first flash, both the same shape:** the offset rule existed
in one code path and a second path did the same job differently. Collapsed to a single
`syncPanelOffset()`. `setTopOffset` went from three call sites to one.

### 3. #51 — uptime reads as time

Raw milliseconds became `HH:MM:SS`. **It exposed a bug worth knowing about:** both P4 boards showed
character glitches, because `:` and `d` were not in the generated numeric font subset. A missing
glyph renders as tofu with no build error. **This exact failure mode comes back in Part Two.**

### 4. 2.6 — vertical swipes

Down-right opens the drawer, down-left the log, up shows the deck, a hidden header peeks for 3 s
before a second swipe commits, tap anywhere dismisses. Edge-gated; swipe distance is `sc(50)` so it
is the same *physical* gesture on a 165 PPI panel and a 294 PPI one.

**Three separate root causes had to be fixed before any of it worked:**

1. Cards swallowed the gesture — every swipe starting on a card read as `{0,0}`.
2. The press origin was captured on the wrong object.
3. The touch was still held when the action ran, so the next gesture inherited the previous one.

**The third one cost a day.** A scripted edit meant to fix it never applied, because the anchor
string contained an escape the shell mangled, so the replace matched nothing and the script
reported success. Three user-visible bugs were blamed elsewhere. That is why the file-editing rule
is now at the very top of `CLAUDE.md`.

Your verdict after testing: *"rock solid"*.

**The best find of the day cost nothing.** Before downloading anything I checked what already

### 6. Both transports, and why that is not redundancy

You asked whether REST and websocket do the same job. Nearly — and the gap is specific:

> **HA's websocket API has no per-entity state call.** `get_states` is all-or-nothing, and on your
> instance that is **787 KB**. REST's `GET /api/states/<id>` is **399–843 bytes**.

| Job | Transport |
|---|---|
| auth, registries | WS |
| **initial value, per entity** | **REST** |
| **live changes** | **WS** `subscribe_trigger` |
| `call_service` (#44) | WS |
| publishing *our* entities | MQTT, unchanged |

**The 30 s delay goes away, and it was never REST's fault** — it is what *polling* costs. Both
reference projects poll on a timer. WS is push.

### 7. Things measured against your live instance

Nothing below was assumed. All read-only except where noted.

| Finding | Number |
|---|---|
| `subscribe_trigger` vs `subscribe_events` | **0 bytes vs 913 KB/min.** ~100x |
| Request ids must strictly increase | `id_reuse`, returned **per request**, not as a disconnect |
| A reconnect is a **cold start** | HA discards subscriptions with the connection |
| **HA serves Fahrenheit** | all 7 temperatures |
| `call_service` echo | **~91 ms** |
| Area resolution, server-side | **818 B** vs the device registry's **115,742 B** |

**`call_service` was exercised on `light.office_overhead`** with your permission — on, off, left
exactly as you had it. **#44's HA half now has no unknowns.**

**The Fahrenheit one matters more than it looks.** HA converts to your display unit before sending.
The same deck probe reads **53.276 °F** over the websocket and **~11.8 °C** over Zigbee2MQTT. Both
correct. The page converts only when the source says `C`, so both land on °F on screen — but
**never infer a unit from a `device_class`**.

**The area one supersedes the design doc.** `ha-websocket.md` §4 said to stream the 120 KB device
registry. It would never have worked: the reassembly buffer is 8 KB. HA's `area_name()` does the
entity→device hop server-side for 818 bytes. **Documented, deliberately not implemented** — your
areas are hardcoded and correct, so it changes nothing visible today. It earns its keep when you
want pages grouped by area.

### 8. #56 — "unavailable" is a statement, not a missing value

**This was a live bug.** HA sends `unavailable` as a literal state and **both** receive paths were
dropping it, so a sensor HA had given up on kept displaying its last good reading indefinitely.

`Entity::available`, a new `ST_UNAVAILABLE` card state that **takes the card body**, not just a
badge.

**It nearly got away from me.** I added the state, the colours and the tag — and it would *still*
have shown the stale number, because `stateColor()` returns early for anything
`cardStateOwnsBody()` rejects. The same lie with a label on it.

### 9. #57 — two clocks, because they answer different questions

`lastUpdateMs` is the **transport's** clock and moves on every message including repeats.
`lastChangeMs` is the **thing's** clock — "the garage has been open for 40 minutes".

Deriving either from the other is wrong in both directions: an MQTT sensor republishing every 30 s
would claim it just changed; an HA entity on a change-driven feed would look unchanged forever
purely because nothing was said.

**Nothing reads it yet.** `heldForMs()` exists and has no caller — that is a card-facing decision
for 2.7.

### 10. Icons — now measured instead of curated

**`scripts/scan_ha_icons.py`** asks your instance what it actually serves.

**Your 18 needed five glyphs we did not have**: `ceiling-light-outline`, `light-recessed` (three
lights), `coach-lamp`, `garage`, `garage-open`. All shipped, ~2 KB across ten faces.

**Your Hue pack is a non-issue.** 1,662 entities use 93 distinct icon strings — **91 MDI, 2 Hue**,
across 4 entities. Covering your whole instance would mean 68 more names.

**Fallback already worked and I verified it:** unknown name → `device_class` → domain. **It never

**The generator was lying to me.** Its cache skipped on file existence alone, so adding a glyph

## Gotchas — must know

- **`export PYTHONIOENCODING=utf-8` before any piped `pio` command.** Otherwise it crashes with
  `UnicodeEncodeError` while writing its own output, which looks *exactly* like a hang. It also
  orphans `esptool`, which then holds your COM port and `firmware.bin` and produces a filesystem
  error that points nowhere near the cause. This cost four attempts today.
- **`Serial` does not come out of the port you flash through.** Six of eight environments set
  `ARDUINO_USB_CDC_ON_BOOT=1`, routing `Serial` to native USB. `WS_P4_5` is the one explicitly set
  to `0`. A `VID_303A` port is the log; a `VID_1A86` port is a CH343 bridge and is not.
- **Do not reflash the P4 boards** until you have decided the soak is over.
- **A missing glyph is silent.** If you ever see tofu, check the font stamp first.
- **`staleAfterMs` is 0 on all 18 HA entities deliberately.** Silence carries no information on a
  change-driven feed. Death is reported by #56, not by a timeout.

## LATER THE SAME DAY — #60 and #44 also landed

### #60 — PAUSE now does something

**Before:** long-press changed a colour and printed `PAUSED`. Exactly one line read the flag. Your
words: *"anything I pause continues to update and even remains interactive"*.

**Now:** the flag lives on the **Entity**, not the Card. A card is a view; "this probe is broken,
stop sending bogus data" is a statement about the probe. Same call this project already made for
`cmdFailed`, after a per-card bitmask let two cards on one switch disagree.

| Entity | What pause does |
|---|---|
| ours (`advertise = true`) | stops publishing, tells HA `unavailable` **once** |
| theirs (`advertise = false`) | stops **applying** inbound values |

Either way the value stops changing, so the frozen display is free — deliberately not "stop
rendering", which would leave the registry and the screen disagreeing. Your stronger rule is in:
**all conditional evaluation stops**, and an optimistic write in flight is abandoned rather than
left to time out as a failure you did not cause.

**Persisted in NVS** and restored after every provider registers. **Listed in the system dump** —
a pause that outlives a reboot is a setting, and a setting with no inventory is a trap.

Written with ESP-IDF `nvs.h` rather than Arduino `Preferences`, per your portability constraint;
that file now pulls in no Arduino header at all.

### #44 — outbound commands

`commandValue()` has existed since #10 and **nothing ever transmitted it**. Now a card tap becomes
a real command.

`CommandRouter` is the only code that knows a command can travel two ways. The registry stays
transport-agnostic.

- **HA entities** -> websocket `call_service`. **The domain comes from the entity id**, not from
  `kind` - your `switch.tv_room_switch_1` is declared a LIGHT because that is what it is in the
  room, and calling `light.turn_on` on it would fail.
- **MQTT entities** -> publish to `commandRef`, a new descriptor field. Retain is **false** and
  must stay false: a retained command is an instruction replayed on every reconnect forever.
- **Ours** -> the optimistic value already is the truth.
- **Paused** -> refused, per #60.

Discovery now emits `cmd_t` for writable commandable platforms, and **`HaPublisher`'s old warning
is gone** because the case is handled. It is retargeted at the opposite mistake: a read-only value
declared as a commandable kind, which HA would now draw as a control that cannot work.

**What #44 did NOT finish, and why that is fine today.** Nothing subscribes to our own `/set`
topics. `MqttManager::subscribeCommand()` exists and has no caller - because **no entity in the
fleet is both writable and advertised**, so there is nothing to subscribe for. The virtual test
switches are `advertise = false` on purpose. The day a real one arrives, that hook is where it
goes.
